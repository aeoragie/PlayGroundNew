# AWS 네트워크 기초 — 리전 · AZ · VPC · 서브넷

> EC2를 만들 때 **"서브넷을 선택하세요"** 에서 막히는 이유를 이해하기 위한 문서다.
> 우리 서버의 실제 값(`172.31.0.0/16`)을 예로 든다. 실제 구축 절차는 `Deploy/AwsSetup.md`.

## 큰 그림 — 다섯 겹의 상자

```
리전 (ap-northeast-2, 서울)
└── 가용 영역 AZ (2a · 2b · 2c · 2d — 서로 떨어진 데이터센터)
    └── VPC (172.31.0.0/16 — 내 전용 사설 네트워크)
        └── 서브넷 (172.31.16.0/20 — VPC를 쪼갠 한 덩어리, AZ 하나에 속한다)
            └── EC2 인스턴스 (사설 IP 172.31.22.197을 여기서 받는다)
```

**바깥에서 안으로 하나씩 고르는 구조**다. 서브넷을 못 고르면 인스턴스를 만들 수 없다 —
"이 서버를 어느 건물, 어느 방에 놓을지"가 정해지지 않은 상태이기 때문이다.

---

## 1. 리전과 가용 영역(AZ)

**리전** = 지리적 위치. 서울(`ap-northeast-2`), 버지니아(`us-east-1`) 등.

- **거의 모든 자원이 리전에 묶인다** — 인스턴스·EBS·S3 버킷·Elastic IP.
  리전을 잘못 고르면 나중에 옮기는 게 아니라 **다시 만들어야 한다.**
- 한국 사용자 기준 왕복 지연: 서울 **10ms대**, 버지니아 **200ms대**.

### 가용 영역(AZ)

**한 리전 안의, 물리적으로 떨어진 데이터센터 묶음.** 서울은 `2a`·`2b`·`2c`·`2d` 4개다.

핵심은 **독립성과 근접성을 동시에 가진다**는 것이다.

- **독립** — AZ마다 전원·냉각·네트워크가 따로다. 수 km 떨어져 있어
  한 곳이 정전·화재·침수를 겪어도 다른 AZ는 산다.
- **근접** — 그런데 같은 리전 안이라 전용 회선으로 **1~2ms**에 통신한다.
  DB를 다른 AZ에 두고 실시간 복제해도 체감 지연이 없다는 뜻이다.

이 두 성질 덕분에 **"장애는 격리되지만 하나의 시스템처럼 쓸 수 있다."**
서로 다른 도시에 두면 독립성은 얻어도 지연 때문에 실시간 복제가 어렵다.

#### AZ에 묶이는 것들

| 자원 | AZ에 묶이나 |
|---|---|
| EC2 인스턴스 | **예** — AZ를 넘어 이동 불가 |
| EBS 볼륨(디스크) | **예** — 다른 AZ 인스턴스에 붙일 수 없다. 옮기려면 **스냅샷 경유** |
| 서브넷 | **예** — 서브넷 하나 = AZ 하나 |
| VPC · 보안 그룹 · S3 | 아니오 — 리전 전체 |

> **인스턴스와 EBS가 같은 AZ여야 한다는 점이 실무에서 자주 걸린다.**
> 인스턴스를 다른 AZ로 옮기려면 "이동"이 아니라 스냅샷 → 새 볼륨 → 새 인스턴스다.

#### 함정 — `2a`는 계정마다 다른 물리 시설이다

**AWS는 계정마다 AZ 이름을 섞어서 매핑한다.** 내 계정의 `ap-northeast-2a`와
다른 사람의 `ap-northeast-2a`가 물리적으로 다른 건물일 수 있다.
모두가 "a부터 쓰자"고 몰리는 것을 막기 위해서다.

진짜 물리 식별자는 **AZ ID**(`apne2-az1` 형태)다. 계정 간에 AZ를 맞춰야 할 때만 쓴다.

```bash
aws ec2 describe-availability-zones --region ap-northeast-2 \
  --query 'AvailabilityZones[].[ZoneName,ZoneId]' --output table
```

#### 비용 — AZ를 넘으면 돈이 든다

같은 AZ 안의 통신은 무료지만, **AZ 간 통신에는 GB당 데이터 전송 요금이 붙는다.**
앱과 DB를 다른 AZ에 두면 모든 쿼리가 과금 대상이 된다.

#### 우리 경우

**서버가 한 대라 어느 AZ를 골라도 상관없다.** AZ가 의미를 갖는 건
같은 것을 **둘 이상** 둘 때다 — 로드밸런서 뒤에 여러 AZ의 서버, RDS Multi-AZ 같은 구성.
지금은 AZ 하나가 죽으면 서비스도 멈춘다. 이는 **알고 받아들인 선택**이다
(투자 유치 단계의 비용 우선).

## 2. VPC — 내 전용 사설 네트워크

**VPC(Virtual Private Cloud)** = AWS 안에 만든, 나만 쓰는 네트워크 공간.

우리 것은 `172.31.0.0/16`이다. 계정을 만들면 리전마다 **기본 VPC**가 하나씩 생겨 있다.

### CIDR 표기 읽는 법

IP 주소는 **32비트**다. `172.31.0.0`은 사람이 읽기 쉽게 8비트씩 넷으로 끊어 적은 것뿐이다.

```
172   .  31   .   0    .   0
10101100 00011111 00000000 00000000     ← 실제로는 이 32비트
└──── /16 = 앞 16비트 고정 ────┘└─ 나머지 16비트는 자유롭게 ─┘
```

**`/16` = "앞에서 16비트는 고정, 나머지는 마음대로"** 라는 뜻이다.
그래서 주소 개수는 **2^(32 − 프리픽스)** 로 계산된다.

| 표기 | 고정 | 주소 개수 | 실제 범위 |
|---|---|---|---|
| `0.0.0.0/0` | 없음 | 전부 (약 43억) | 모든 주소 = **"그 밖의 모든 곳"** |
| `172.31.0.0/16` | 앞 16비트 | 2^16 = **65,536** | `172.31.0.0` ~ `172.31.255.255` |
| `172.31.16.0/20` | 앞 20비트 | 2^12 = **4,096** | `172.31.16.0` ~ `172.31.31.255` |
| `172.31.22.197/32` | 32비트 전부 | 2^0 = **1** | 그 주소 딱 하나 |

**숫자가 클수록 좁다.** 보안 그룹에서 "내 IP만"을 고르면 `1.2.3.4/32`로 들어가는 게 이것이다.

#### `/20`의 범위가 왜 `16 ~ 31`인가

`/20`은 셋째 옥텟(8비트) 중 **앞 4비트까지** 고정한다는 뜻이다(16 + 4 = 20).

```
셋째 옥텟 = 16  →  0001 0000
                  └──┘ 고정   └──┘ 자유 (4비트 = 16가지)
→ 0001 0000(16) 부터 0001 1111(31) 까지
```

그래서 `172.31.16.0/20`은 **`172.31.16.x` ~ `172.31.31.x`** 를 덮는다.
기본 VPC의 서브넷이 `0/20`·`16/20`·`32/20`·`48/20`으로 16씩 뛰는 이유다.

#### 함정 — AWS는 서브넷마다 5개를 가져간다

서브넷 CIDR의 주소를 전부 쓸 수 있는 게 아니다. **앞의 4개와 마지막 1개는 예약**이다:

| 주소 (`172.31.16.0/20` 기준) | 용도 |
|---|---|
| `172.31.16.0` | 네트워크 주소 |
| `172.31.16.1` | **VPC 라우터** |
| `172.31.16.2` | **DNS** |
| `172.31.16.3` | 향후 사용 예약 |
| `172.31.31.255` | 브로드캐스트 |

그래서 `/20`은 4,096개가 아니라 **4,091개**를 쓸 수 있다.
`/28`(16개)을 잡으면 **11개**뿐이라 작은 서브넷을 만들 때 실제로 걸린다.

#### 제약

- **VPC CIDR은 `/16` ~ `/28`** 만 가능하다 (더 크게도 더 작게도 못 잡는다).
- **서브넷 CIDR은 VPC 범위 안**에 있어야 하고, 서브넷끼리 **겹치면 안 된다.**
- VPC CIDR은 만든 뒤 **줄일 수 없다** — 추가 대역을 붙이는 것만 된다. 처음에 넉넉히 잡는다.

#### 사설 대역

인터넷에서 직접 찾아올 수 없도록 예약된 범위다. 집 공유기가 주는 `192.168.0.x`와 같은 성격이다.

| 대역 | 크기 | 흔한 용도 |
|---|---|---|
| `10.0.0.0/8` | 1,677만 | 대규모 사내망 · 직접 만든 VPC |
| `172.16.0.0/12` | 104만 | **AWS 기본 VPC가 여기** (`172.31.0.0/16`) |
| `192.168.0.0/16` | 65,536 | 가정용 공유기 |

> **VPN이나 회사망과 연결할 계획이 있으면 대역이 겹치지 않게 잡아야 한다.**
> 양쪽 다 `192.168.0.0/16`이면 어느 쪽으로 보낼지 정할 수 없어 연결 자체가 안 된다.

## 3. 서브넷 — VPC를 쪼갠 한 덩어리

**서브넷 = VPC의 주소 범위를 잘라낸 조각이고, 반드시 AZ 하나에 속한다.**

기본 VPC에는 보통 AZ마다 서브넷이 하나씩, `/20` 크기로 만들어져 있다:

| 서브넷 | AZ |
|---|---|
| `172.31.0.0/20` | ap-northeast-2**a** |
| `172.31.16.0/20` | ap-northeast-2**b** |
| `172.31.32.0/20` | ap-northeast-2**c** |
| `172.31.48.0/20` | ap-northeast-2**d** |

### 왜 서브넷을 골라야 하나 — 이유 셋

**① AZ가 결정된다.** 인스턴스는 물리적으로 어딘가에 있어야 한다.
서브넷을 고르는 행위가 곧 **"어느 데이터센터에 놓을지"** 를 고르는 것이다.

**② 사설 IP가 여기서 나온다.** `172.31.16.0/20` 서브넷에 인스턴스를 만들면
`172.31.22.197` 같은 주소를 받는다 — 앞서 본 **비공개 IP가 바로 이것**이다.

**③ 인터넷에 나갈 수 있는지가 여기서 갈린다.** 다음 절.

## 4. 인터넷 게이트웨이(IGW)

**VPC와 인터넷을 잇는 문.** VPC 하나에 **하나만** 붙일 수 있다.

### 하는 일이 둘이다

**① 라우팅의 목적지가 되어 준다** — 라우팅 테이블에 `0.0.0.0/0 → igw-…`를 쓸 수 있게 한다.

**② 주소를 바꿔치기한다 (NAT).** 이게 처음에 가장 헷갈리는 부분이다.

```
인스턴스 OS가 아는 자기 주소 :  172.31.22.197   (사설)
인터넷에서 보이는 주소       :  43.201.x.x      (Elastic IP)

나갈 때  : 출발지를 172.31.22.197 → 43.201.x.x 로 바꿔서 내보낸다
들어올 때: 목적지를 43.201.x.x → 172.31.22.197 로 되돌려 넣는다
```

**서버 안에서 `ip addr`를 쳐도 공인 IP가 안 보이는 이유가 이것이다.**
OS는 끝까지 사설 주소만 안다. 공인 IP는 IGW가 바깥에서 갈아 끼운다.

> 그래서 앱이 "요청자의 IP"를 알려면 Nginx가 넘겨주는 `X-Forwarded-For`가 필요하다.
> 우리 `playground.conf`가 그 헤더를 세팅하고, `Program.cs`의 `UseForwardedHeaders`가 읽는다.

### 성질

- **요금이 없다** (게이트웨이 자체는 무료. 나가는 데이터 전송 요금은 별개)
- **대역폭 병목이 없다** — AWS가 알아서 수평 확장한다. 성능을 걱정할 대상이 아니다
- **AZ에 묶이지 않는다** — VPC 전체가 공유한다

### NAT 게이트웨이와 헷갈리지 않기

| | 인터넷 게이트웨이 | NAT 게이트웨이 |
|---|---|---|
| 방향 | **양방향** — 밖에서 들어올 수도 있다 | **나가기만** — 밖에서 못 들어온다 |
| 쓰는 곳 | 퍼블릭 서브넷 | **프라이빗** 서브넷 |
| 용도 | 웹 서버 공개 | DB가 보안 패치만 받아 오게 |
| 요금 | 무료 | **시간당 + GB당 유료** |

**우리는 IGW만 쓴다.** 서버가 한 대이고 그 한 대가 웹을 서비스해야 하므로
퍼블릭 서브넷에 있어야 한다. NAT 게이트웨이는 DB를 프라이빗으로 분리할 때 필요해진다.

## 5. 퍼블릭 서브넷 vs 프라이빗 서브넷

**서브넷 자체에 "퍼블릭"이라는 설정값은 없다.** 붙어 있는 **라우팅 테이블**이 결정한다.

```
퍼블릭 서브넷   : 0.0.0.0/0 → 인터넷 게이트웨이(IGW)   ← 인터넷과 오간다
프라이빗 서브넷 : 0.0.0.0/0 경로가 IGW로 가지 않음      ← VPC 안에서만
```

라우팅 테이블은 **긴 것이 이긴다**(longest prefix match). 기본 VPC의 라우팅 테이블은 이렇다:

| 대상 | 목적지 | 의미 |
|---|---|---|
| `172.31.0.0/16` | `local` | **VPC 안끼리는 IGW를 안 거친다** (지울 수 없는 규칙) |
| `0.0.0.0/0` | `igw-…` | 그 밖의 전부 → 인터넷 |

**웹 서버가 인터넷에서 보이려면 세 가지가 다 필요하다:**

1. VPC에 **IGW가 붙어 있을 것**
2. 서브넷의 라우팅 테이블에 **`0.0.0.0/0 → IGW`** 가 있을 것 (= 퍼블릭 서브넷)
3. 인스턴스가 **공인 IP를 가질 것** — `퍼블릭 IP 자동 할당 = 활성화` 또는 Elastic IP

> 하나라도 빠지면 증상은 똑같이 **"연결 시간 초과"** 다. 위에서부터 순서대로 확인한다.

> **우리는 Elastic IP를 붙인다.** 자동 할당 IP는 인스턴스를 중지·시작하면 **바뀌어서**
> 도메인(A 레코드)과 보안 그룹 설정이 전부 어긋난다.

### 우리 구성에서는

지금은 **한 대에 앱·DB·Redis가 다 있으므로 퍼블릭 서브넷 하나면 충분하다.**
DB를 별도 인스턴스나 RDS로 분리하면 그때 DB를 프라이빗 서브넷에 넣는다 —
**DB가 인터넷에서 아예 보이지 않게** 하는 것이 원래 모양이다.

## 6. 방화벽은 세 겹이다 (헷갈리기 쉬운 부분)

| 무엇 | 어디에 붙나 | 성격 | 우리 설정 |
|---|---|---|---|
| **보안 그룹** | 인스턴스 | **상태 저장** — 나간 요청의 응답은 자동 허용. **허용 규칙만** 있다 | 22·47821은 내 IP, 80·443은 전체 |
| **네트워크 ACL** | 서브넷 | 상태 비저장 — 들어오고 나가는 걸 각각 써야 한다 | 기본값(전부 허용) 그대로 |
| **ufw** | 리눅스 OS 안 | 호스트 방화벽 | 22·80·443·47821 |

**보안 그룹과 ufw를 둘 다 통과해야 한다.** 하나만 막혀도 증상은 똑같이 "시간 초과"라
원인을 착각하기 쉽다. NACL은 기본값이 전부 허용이라 평소엔 신경 쓰지 않는다.

## 7. "서브넷을 찾을 수 없습니다" 해결

기본 VPC는 있는데 **그 안에 서브넷이 없는 상태**다. 기본 서브넷이 지워졌을 때 생긴다.

### 방법 A — 기본 서브넷을 되살린다 (권장)

1. **VPC** 콘솔 → 좌측 **서브넷** → **서브넷 생성**
2. **VPC**: `vpc-0016d380c93115f70` (172.31.0.0/16) 선택
3. 서브넷 설정:
   - 이름: `playground-public-2a`
   - 가용 영역: **ap-northeast-2a**
   - IPv4 CIDR: **`172.31.0.0/20`**
4. **생성**

만든 서브넷을 퍼블릭으로 만든다:

5. 서브넷 선택 → **작업** → **서브넷 설정 편집** → **퍼블릭 IPv4 주소 자동 할당** 체크
6. **라우팅 테이블** 탭 확인 — `0.0.0.0/0 → igw-…`가 있어야 한다.
   없으면 → 좌측 **인터넷 게이트웨이**에 IGW가 있는지 보고, 없으면 만들어 VPC에 연결한 뒤
   라우팅 테이블에 `0.0.0.0/0 → IGW` 경로를 추가한다.

### 방법 B — 기본 VPC를 통째로 다시 만든다

기본 VPC까지 손상됐다면 이쪽이 빠르다. **IGW·라우팅·AZ별 서브넷이 한 번에 만들어진다.**

- **VPC** 콘솔 → **작업** → **기본 VPC 생성**
- 기존 기본 VPC가 남아 있으면 먼저 지워야 한다 — **그 안에 쓰는 자원이 없을 때만**.

> 지금은 아무것도 안 올라가 있으니 B가 안전하고 빠르다.
> 나중에 자원이 올라간 뒤에는 절대 이렇게 하지 않는다.

### 그다음

인스턴스 생성 화면으로 돌아가 **서브넷** = 방금 만든 것, **퍼블릭 IP 자동 할당** = **활성화**.
(Elastic IP를 붙일 거라 자동 할당 IP는 어차피 대체되지만, 활성화해 두면
Elastic IP를 연결하기 전에도 접속해 볼 수 있다.)

## 용어 한 줄 정리

| 용어 | 한 줄 |
|---|---|
| 리전 | 지리적 위치. 자원이 여기 묶인다 (서울 = ap-northeast-2) |
| 가용 영역(AZ) | 리전 안의 분리된 데이터센터. 독립돼 있으면서 1~2ms로 가깝다. 서울은 4개 |
| AZ ID | `apne2-az1` — **진짜 물리 식별자**. `2a`라는 이름은 계정마다 다른 곳을 가리킨다 |
| VPC | 내 전용 사설 네트워크 (172.31.0.0/16) |
| 서브넷 | VPC를 쪼갠 조각. **AZ 하나에 속한다**. 앞 4개 + 마지막 1개 주소는 AWS가 예약 |
| CIDR | 주소 범위 표기. 개수 = 2^(32−프리픽스). `/` 뒤 숫자가 클수록 좁다 |
| 인터넷 게이트웨이(IGW) | VPC를 인터넷과 잇는 문. **공인 IP ↔ 사설 IP 변환도 여기서** 한다. 무료 |
| NAT 게이트웨이 | 프라이빗 서브넷이 **나가기만** 할 때. 유료 — 우리는 안 쓴다 |
| 라우팅 테이블 | 어디로 보낼지의 규칙. **퍼블릭/프라이빗을 가르는 것** |
| 보안 그룹 | 인스턴스 방화벽. 허용 규칙만, 상태 저장 |
| 네트워크 ACL | 서브넷 방화벽. 기본은 전부 허용 |
| Elastic IP | 고정 공인 IP. 붙여야 재시작해도 안 바뀐다 |
| 사설 IP | 서브넷에서 받는 내부 주소(172.31.x.x). 인터넷에서 접근 불가 |
