## R1. 기능 마감 (다듬기)

목적: "만들다 만 것"을 없앤다. 새 기능은 만들지 않는다.

### R1-1. P1 잔여 처리 여부 결정 → 처리 또는 명시적 보류

CLAUDE.md의 소소한 잔여 7건. **전부 할 필요는 없다 — 각각 "첫 배포에 필요한가"로 잘라낸다.**

| 항목 | 첫 배포에 필요한가 (제안) |
|---|---|
| 요청 취소 링크 | 필요 — 사용자가 되돌릴 길이 없으면 문의로 이어진다 |
| 삭제 시 팀원 알림 발송 훅 | 필요 — 조용히 사라지면 신뢰 문제 |
| 일정 반복 · 월 전환 | 보류 — 없어도 일정 등록은 된다 |
| 코치 계정 권한 | 보류 — 관리자 단독 운영으로 시작 가능 |
| 증빙 사진 첨부 | 보류 — 수정 신청 심사 주체(대회 서비스)가 아직 없다 |
| 배너 3톤 생산자 | 보류 — 운영 공지 수단이 아직 필요 없다 |
| 공개 프로필 강점 태그 카드 PNG | 보류 — 카드 공유는 동작하고 태그만 빠진다 |

> 보류는 **문서에 남긴다** — 나중에 "왜 없지?"가 되지 않도록.

### R1-2. 전 화면 수동 검수 (S1~S7)

`Handoff/TEST.INTEGRATIONSCENARIOS.md`의 7개 여정을 실제로 돌며 결함 목록을 만든다.
발견 결함은 `시나리오번호-순번: 화면 / 재현 / 기대 vs 실제`로 기록하고, 고칠 것/보류할 것을 나눈다.

**공통 확인(모든 시나리오에 겹침)**: 이모지 0 · 한글 줄바꿈 결함 0 · 모바일 390px 터치 44px+ ·
폼 오류는 전부 인라인 · 콘솔 에러 0 · 죽은 링크 0.

### R1-3. 빈 데이터 화면 점검

생산자가 없어 비는 화면(공식 기록·순위표·경기 상세·에이전트 표면)이 **레이아웃 붕괴 없이
빈 상태로 보이는지** 확인한다. D6 결정에 따라 시드를 넣거나 안내 문구를 확정한다.

**완료 기준** — 검수 결함 목록이 "고침" 또는 "보류(사유 기재)"로 전부 닫힘.

## R3. 프로덕션 하드닝

목적: 스텁을 실물로 바꾼다. **전부 포트 뒤에 있어 어댑터 교체 중심**이다.

| # | 항목 | 현재 | 할 일 | 선행 |
|---|---|---|---|---|
| H1 | 이메일 | `LogOnlyEmailSender` (37줄) | 실제 발송 어댑터 + 실패 재시도 | D3 |
| H2 | 이미지 | `LocalImageStorageService` (63줄) | S3 어댑터 + 공개 URL 규칙 | D1 |
| H3 | export 큐 | 인메모리 `Channel`(무제한) | **재시작 시 유실** — DB 상태 기반 복구 or 지속 큐 | — |
| H4 | JWT 무효화 | 없음 | 로그아웃·탈퇴·역할 변경 시 기존 토큰 차단(세션 저장소) | — |
| H5 | OG 이미지 폰트 | Linux 네이티브 패키지는 참조됨, 한글은 **시스템 폰트 의존** | 컨테이너/호스트에 한글 폰트 설치 확인 | D1 |

## R4. 배포 파이프라인 완성

목적: `deploy.yml`의 placeholder를 실물로 바꾸고 **되돌릴 수 있게** 만든다.

1. **D1·D2 확정** → 배포 방식 결정(컨테이너 vs 파일 배포)
2. `deploy.yml`의 Staging·Production 스텝 실제 구현 (현재 `echo`만 있음)
3. **GitHub Environments 시크릿 등록** — `Jwt__Key`, OAuth 시크릿, DB 커넥션 (`__`가 계층 구분자)
4. **Production에 Required reviewers 설정** — 승인 게이트(워크플로 주석에 이미 안내됨)
5. **DB 마이그레이션 배포 절차 확정** — `Source/Database/*/Migrations/` 순차 적용을 누가/언제
6. **롤백 절차 문서화** — 앱 롤백 + 마이그레이션은 되돌릴 수 없는 변경이 있는지 점검
7. Staging 배포 → R1-2 검수 재실행 → Production 승인 배포

**완료 기준** — Staging·Production이 파이프라인으로 배포되고, 롤백을 1회 실제로 연습해 봄.

## 순서와 병행

```
R1 기능 마감 ─┐
              ├─→ R3 하드닝(H3·H4 먼저) ─→ R4 배포 ─→ R5 운영
R2 테스트 ────┘        ↑
                   D1~D4 결정 필요(H1·H2·H5·H6)
```

- **R1·R2는 지금 바로, 결정 없이 시작 가능** — 여기부터 하는 게 맞다
- **R3의 H3(export 내구성)·H4(JWT 무효화)도 결정 무관** — R2와 병행
- D1~D4가 정해지는 대로 H1·H2·H5·H6 → R4

## 권장 착수 순서

1. **R2-1 DB 프로시저 계약 테스트** — 안전망의 가장 큰 구멍이고, 이후 모든 수정의 바닥이 된다
2. **R1-2 전 화면 수동 검수** — 결함 목록이 나와야 R1-1의 "필요/보류" 판단이 근거를 얻는다
