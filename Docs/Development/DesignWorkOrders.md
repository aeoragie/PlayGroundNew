# 클로드디자인 작업지시서 (남은 디자인 필요 항목)

> 코드 구현은 대부분 소진됐고, 남은 실질 작업은 **스키마+화면 디자인이 선행**돼야 하는 것들이다.
> 각 프롬프트를 그대로 클로드디자인에 붙여넣어 핸드오프(README + SPEC + dc.html)를 받는다.
> 우선순위: **A(화면·스키마) → B(결정 문서) → C(인프라·후속)**. A 안에서는 ①일정 → ②지원 → ③강점태그 권장.

---

## 공통 머리말 — 매 프롬프트 앞에 붙일 것

```
기존 PlayGround 디자인 시스템을 그대로 계승해. 토큰은 Handoff/Design.Landing.Phase0
(오렌지=CTA 5~10%, 네이비=신뢰, teal=뱃지·체크, violet=에이전트 전용), 공용 패턴 15종은
Handoff/Design.PatternsIndex/README.md의 결정표에서 먼저 찾고 없을 때만 새로 만들어.
산출물은 기존 핸드오프와 같은 구조로: README.md(개요·규칙·데이터·경계) + SPEC.*.md
(섹션 순서·카피 고정·완료 체크리스트) + *.dc.html(PC) + * Mobile.dc.html(모바일).
카피는 한 글자도 바꾸지 않는 확정 텍스트로 써. "빈 데이터 노출 금지"·"행당 뱃지 1개"·
"폼 오류 인라인만"·"공식 기록의 주체는 주최측(설계 결정 7)"·"연락처는 서버 마스킹" 규칙 준수.
경계가 애매하면 스키마·API·화면의 책임 범위를 명시적으로 나눠서 써.
```

## A. 화면·스키마 신설 (구현 착수하려면 이게 먼저)

### ① 일정 (Schedule) — 최우선, 3곳 동시 해소

```
Handoff/Design.TeamDashboard의 일정 섹션과 Design.DashboardHub의 "다음 경기 줄",
Design.TeamPublicHome을 참고해 팀 일정(Schedule) 핸드오프를 만들어. 팀 관리자가 일정을
추가(경기·훈련·대회, 날짜·시간·장소·상대·공개여부)하고, 공개 홈페이지와 허브 "다음 경기"에
자동 노출되는 흐름. 날짜·시간은 Design.DatePicker 공용 컴포넌트(캘린더 PastOnly/FutureOnly)
재사용. 유형별 pill 색(경기=네이비/대회=오렌지톤/훈련=teal)은 기존 SPEC 유지. 스키마
(SoccerSchedules 성격) 컬럼과 상태(예정/종료 자동 파생), 공개홈 노출 규칙, 구독 캘린더
(Google/Apple) 자리까지 명세해. 지난 일정 아카이브·반복 일정은 P1로 분리.
```

### ② 지원 (Application) — 획득 루프 완성

```
Handoff/Design.TeamPublicHome §④ 모집 탭과 Design.TeamDashboard 모집 섹션을 참고해
지원(Application) 핸드오프를 만들어. 게스트/선수가 모집 공고에 "지원하기"(이름·연락처·
자기소개·희망 포지션), 팀 관리자가 지원자 리스트를 보고 상태 전환(접수→검토→수락/보류),
에이전트 추천 파이프라인까지. 상태 뱃지·⋯ 액션은 기존 Design.DropdownMenu·상태 뱃지 톤
규칙 준수. 지원 스키마·중복 지원 방지·알림(팀에게 새 지원) 발송을 명세해. 연락처는 서버
마스킹 원칙 유지. **모집 공고와의 연결**(어느 공고에 대한 지원인지)과 수락 시 로스터 편입
동선까지 경계를 그어.
```

### ③ 강점 태그 — 작고 독립적

```
Handoff/Design.PlayerDashboard와 Design.PlayerPublicProfile을 참고해 선수 강점 태그
핸드오프를 만들어. 선수 대시보드 프로필에서 강점 태그(예: "빠른 스피드"·"왼발 킥")를 최대
N개 입력(칩 입력, 자유 텍스트 또는 프리셋), 공개 프로필 히어로/요약에 노출. 저장 스키마
(태그 배열)·개수·길이 상한·공개 범위(SoccerPlayerFieldVisibilities 항목별 공개 설정과의
관계)를 명세. 태그 칩은 기존 분류 칩 스타일 재사용.
```

### ④ 팀 P1 4종 — 큰 덩어리, 하나씩

```
Handoff/Design.TeamDashboard P1 예정 4종(팀 게시판·회비·출결·메시지)을 각각 별도
핸드오프로 만들어(한 번에 하나씩 지시할 테니 우선 팀 게시판부터). 팀 게시판: 관리자·코치가
공지/자료를 올리고 로스터 보호자가 열람, 공개홈 노출 여부 선택. 스키마·권한(작성=관리자·코치/
열람=소속 보호자)·⋯ 편집/삭제·빈 상태를 명세.
```
> 이후 회비·출결·메시지는 게시판 확정 후 같은 틀로 하나씩 지시.

### ⑤ 에이전트 축 — 3번째 축, 전략 결정 포함

```
Handoff/Design.AgentViewApproval과 설계 결정 4(에이전트 축 선반영)를 참고해 에이전트
대시보드·프로필 핸드오프를 만들어. 에이전트가 선수 열람 요청을 생성하는 화면, 자기 프로필
(신원·소속·인증), 승인/거절/만료 이력, denied "재승인 요청 기록" 화면. feature flag 뒤에
두는 전제, 요청 생성이 에이전트 서비스의 몫인 경계, 30일 만료·차단 규칙을 명세. violet
토큰은 에이전트 요소 전용 규칙 유지. **PlayGround(조회·심사·차단)와 에이전트 서비스
(요청 생성·열람 로그·쿨다운)의 책임 분리**를 명확히 그어.
```

### ⑥ Settings 별도 플로우 — 렌더만 있고 무동작인 3종 ⭐신규

```
Handoff/Design.Settings를 참고해 계정 설정의 무동작 3종(이름 변경 · Kakao 연결 · 데이터
내려받기)을 각각 실제 플로우 핸드오프로 만들어. 이름 변경: 확인 단계·중복/제약·반영 범위
(공개 프로필·리뷰 마스킹에 미치는 영향). Kakao 연결: 소셜 계정 연결/해제·이미 연결된 경우.
데이터 내려받기: 무엇을(프로필·기록·요청) 어떤 형식으로 언제 받는지·요청→생성→다운로드 상태.
각각 스키마·API 경계·확인/위험 모달(Design.FeedbackPatterns 3종 Kind)을 명세.
```

## B. 결정 문서 (방향부터 정해야 화면이 나옴)

### ⑦ 팀 탐색 검색 주체 + 랜딩 배선 + GNB 퀵서치

```
팀 탐색(/teams)의 검색 주체를 확정해 줘 — 선수가 팀을 찾는지, 팀이 선수를 찾는지,
에이전트가 둘 다 찾는지에 따라 랜딩 역할 카드 배선·GNB 퀵서치·검색 결과 화면이 달라져.
각 시나리오의 진입 동선과 랜딩 카드 목적지를 정하는 결정 문서 + 확정 시 GNB 퀵서치 SPEC을
만들어. (현재 랜딩 역할 카드는 팀·선수 모두 /login으로 임시 연결돼 있고, GNB 퀵서치는
검색 화면이 없어 미렌더 상태다.)
```

### ⑧ Records 상태 필터 + 순위표 "내 팀 행" 마킹 결정 ⭐신규

```
Handoff/Design.Records를 참고해 두 가지를 확정하는 결정 문서를 만들어(확정되면 SPEC 보강):
1) 경기기록 목록의 상태 처리 — 현재 SPEC은 "진행중→예정→종료 자동 정렬 + 상태 색 범례로
   전부 표시"가 확정 결정이다. 여기에 상태 필터 칩(SearchFilter)을 추가해 일부를 숨길지,
   아니면 지금처럼 전부 표시를 유지할지 정해. 추가한다면 기존 자동 정렬·"올해만+아카이브
   분리"와 어떻게 공존하는지까지.
2) 순위표(Records 상세)의 "내 팀 행" 마킹 — Records 상세는 AllowAnonymous 공개 화면이다.
   "내 팀"의 주체를 무엇으로 볼지(로그인한 팀 관리자의 팀 / 로그인 선수의 소속팀 / 게스트는
   없음) 정하고, 스크롤 밖 상단 고정 요약(TableList 카탈로그)의 노출 조건을 명세해.
```

## C. 인프라·후속 (필요할 때)

### ⑨ OG 메타 (공개 프로필·팀 홈 공유 카드)

```
공개 선수 프로필/팀 홈을 카톡·SNS에 공유할 때 뜨는 OG 메타(제목·설명·썸네일)를 설계해.
PlayGround는 Blazor WASM SPA라 클라이언트 메타로는 크롤러가 못 읽는다 — 서버가 슬러그별로
OG 태그를 렌더하는 방식(경로·캐시·이미지 소스)을 명세. 화면 디자인이 아니라 아키텍처 결정
문서 + 카드 이미지 규격.
```

### ⑩ 라우트형 알림 센터 (`/notifications`)

```
현재 알림 센터는 Design.ClaimFlow 정의대로 GNB 벨 패널로만 존재한다. 전용 라우트(/notifications)
전체 화면이 필요한지 판단하고, 필요하면 목록·필터·읽음/전체 읽음·페이지네이션 SPEC을 만들어.
(불필요하면 "벨 패널로 충분" 결정만 남겨도 됨.)
```
