# DECISION.NOTIFICATIONCENTER — 알림 센터를 라우트로 둘 것인가

> 위치: `Handoff\DECISION.NOTIFICATIONCENTER.md` · DesignWorkOrders ⑩ (마지막 항목)
> 현재 상태: `Design.ClaimFlow`에 알림 센터가 **패널**로 설계·구현됨(GNB 벨 → 드롭다운/모바일 풀스크린). 라우트 `/notifications`는 없음.

## 0. 무엇을 결정하나
알림 센터의 **거처**를 확정한다. 패널만 유지할지, 전용 페이지를 만들지, 절충할지 — 여기에 따라 딥링크·뒤로가기·알림 클릭 동선이 달라진다.

## 1. 대안

| 대안 | 내용 | 문제 |
|---|---|---|
| A. 패널만 (현행) | 벨 클릭 → 드롭다운(PC) / 풀스크린(모바일) | 알림 이메일·푸시에서 "알림 보기"로 들어올 **딥링크 대상이 없다** · 뒤로가기로 목록에 못 돌아옴 · 목록이 길어지면(승인 요청 누적) 패널이 감당 못 함 |
| B. 라우트만 | 벨 클릭 → `/notifications` 이동 | 알림 확인마다 페이지 이탈 — 작업 중이던 화면을 잃는다(대시보드에서 승인 처리하는 흐름을 끊음) |
| **C. 절충 (추천)** | 벨 = 패널 유지(최근 10건) + 패널 하단 "전체 보기" → `/notifications` | 일상 확인은 패널에서 끝나고, 누적·딥링크·검색은 페이지가 받는다 |

## 2. 추천 = C, 근거
1. **딥링크가 필요하다**: 푸시·이메일·카톡 알림톡에서 여는 대상이 있어야 한다(현재는 랜딩으로 보낼 수밖에 없음). `/notifications`가 그 착지점.
2. **패널은 "지금 온 것", 페이지는 "쌓인 것"** — 팀 관리자는 승인 요청이 수십 건 쌓인다(TableList 더 보기 20개 규칙이 필요한 규모). 패널에서 스크롤로 감당할 양이 아님.
3. **이탈 비용 회피**: 대시보드에서 승인 처리하는 주 동선은 패널에서 그대로 끝나야 한다 — 그래서 B는 탈락.
4. 이미 있는 패턴 조합으로 끝난다: PaginationBreadcrumb(뒤로 헤더) + TableList(더 보기·행 3형) + SearchFilter(세그먼트) + EmptyStates. **신규 패턴 없음.**

## 3. 확정 시 명세 (구현 지시)

### 패널 (기존 유지 + 2가지만 변경)
- 최근 **10건**까지만 표시(현행 그대로), 하단에 **"전체 보기 →"** 행 추가 → `/notifications`
- "모두 읽음" 버튼은 패널에 유지

### 라우트 `/notifications` (신규)
- 위치·구조: PC = 컨테이너 max-width 720px 단일 컬럼 / 모바일 = 뒤로 헤더("알림", 상위=대시보드 허브 — PaginationBreadcrumb 규칙: history.back이 아니라 구조상 상위)
- **세그먼트**: 전체 / 처리 필요 / 읽지 않음 — URL 쿼리 동기화(`?filter=action`), SearchFilter 규칙
- **행**: 알림 유형 원(연결=오렌지톤 / 열람=violet / 결과·기록=네이비톤 — 허브 '처리가 필요해요' 칩 톤 계승) + 제목 + 설명 + 상대 시각 + **안읽음 오렌지 점** · 액션형 알림은 우측 버튼(TableList 행 3형: 액션형은 행 탭 없음), 그 외는 내비게이션형(행 전체 탭 + 셰브론)
- **더 보기 20개**(무한 스크롤 금지) · 진입 시 화면에 보인 알림은 읽음 처리(액션 알림은 처리해야 소멸)
- 빈 상태: Tier A "알림이 없어요 / 새 소식이 오면 여기에 모여요"(CTA 없음)
- 딥링크 진입 시 로그인 필요 → `/auth?returnUrl=/notifications`

### 알림 발송 측 규칙(불변 유지)
- 토스트와 알림 센터 **중복 발송 금지**(FeedbackPatterns 결정표)
- 허브 '처리가 필요해요' 섹션은 액션형 상위 3건만 표시하고 초과분은 이 페이지로 유도(현행 유지)
